# Where the data comes from

Every file under `Data/` is generated by a tool in `tools/`. This document
records which tool writes which file, which global the addon reads it from,
and — where it matters — how a field is derived, so a future maintainer can
tell a deliberate choice from an accident.

## How each site is read

### Archon.gg

Next.js. The whole page model — including the spec list, the season's
dungeons and raid bosses, and the difficulty slugs — ships as a
`__NEXT_DATA__` JSON blob. The scraper therefore **discovers** the season
layout instead of hard-coding it, which is what makes a season rollover a
rerun rather than a patch.

Fields worth knowing:

* `talentTree.exportCodeParams.exportCode` — the Blizzard import string.
* `dehydratedBuild.heroSpecId` — resolved to a name via
  `talentTreeBlueprints[*].heroTrees`.
* `alternatives[].popularity` and `isDefaultSelection` — the best build per
  hero talent is kept, with Archon's own pick winning ties.
* `<BadgeLabel>BiS</BadgeLabel>` on an item — this is Archon repeating
  Wowhead's best-in-slot claim, and it is the **only** thing that sets the
  addon's `bis` flag. Archon's own numbers are popularity, which is a
  different claim and must not be relabelled as BiS.

Raid difficulty follows a rank: Mythic beats Heroic beats Normal, filtered
by what is actually published. Early in a season only Normal and Heroic
exist. Normal contexts are dropped for any boss that Heroic already covers,
because the addon buckets every non-Mythic raid context together and would
otherwise list the boss twice.

### Wowhead

Wowhead answers **403 to any client that does not send a full browser
header set** — not just a `User-Agent`, but the `Sec-Fetch-*` and
`sec-ch-ua` headers a real navigation carries. `ccutil.BROWSER_HEADERS`
sends them. With them an existing page returns 200 and a nonexistent one
returns 404, so a missing page can be told apart from a block; without
them every URL looks equally broken.

Wowhead renders guides client-side from a BBCode-like source that ships
inside the HTML as a JavaScript string literal:

```
WH.markup.printHtml("[h2 toc=\"Stats\"]...[/h2]...", ...)
```

`tools/whmarkup.py` extracts and walks it. It is far easier to read than
the rendered DOM, and it is where the machine-usable parts live.

Four traps, each handled in code — worth keeping in mind when extending:

1. **Nesting.** `[tabs]`/`[tab]` nest, and BiS tables can embed a table
   inside a cell. A non-greedy scan to the first closing tag ends the outer
   block early and *silently drops rows*: that cost Enhancement Shaman four
   gear slots before it was noticed. Use `whmarkup.nested_blocks`.
2. **`[url=item=…]` links.** A gear cell can contain both the item and a
   link to an alternative. A bare `[item=…]` match picks up the wrong one;
   the item regex uses a negative lookbehind.
3. **`display-options` is not always a hero talent.** Holy Priest toggles a
   `Tot-ST` build variant the same way Hunter toggles Pack Leader. Only
   options declared `radio="Hero"` name a hero talent — the rest belong in
   the context label.
4. **`$role` placeholders.** Blood Death Knight's nav bar links
   `rotation-cooldowns-pve-$role`, which 404s. The candidates
   (dps / tank / healer) are tried in turn.

Item names are not in the markup — only ids. They come from the page's
`WH.Gatherer.addData(3, 1, {...})` payload, which also carries the icon
slug. The icon is what identifies a consumable's kind: "Light's Potential"
reads like food but its icon is `…alchemy_lightpotion_yellow`, so icon
match runs before name match.

Not scraped: the standalone talent-builds page contributes its export
strings, but its grouping is prose and is recovered heuristically from
surrounding tabs and headings. The stat-priority page is prose throughout
and contributes nothing.

### Icy Veins

Server-rendered; a plain fetch is enough. Talent builds come from
`export-string__title` / `export-string__code` pairs, BiS from the
`bis_<n>_<n>` panels ("Overall" / "Mythic+" / "Raid"). Page URLs are
role-dependent (`-pve-dps-`, `-pve-healer-`, `-pve-tank-`) and are read out
of `sources.lua` rather than reconstructed.

### murlok.io

Server-rendered. Stat priority comes from the `guide-stats-chart-item`
bars, gear from the per-slot lists. Secondaries with a rating of zero are
dropped: a zero is not a priority. At most three items per slot are kept —
past that the tail is noise.

### Blizzard API

`bnet-pvp-talents.lua` holds rated-PvP loadouts per bracket: what the
top-rated players of each spec actually run. There is no aggregate
endpoint, so it walks the PvP leaderboards and reads each listed
character's profile — roughly 2,400 requests, by far the heaviest
scraper here. Responses are cached like everything else.

The `loadouts` array carrying `talent_loadout_code` went missing from the
character specializations endpoint in patch 11.2 (reported 2025-08-07,
never answered by Blizzard). It is back as of season 42 — `probe_bnet.py`
confirms that in four requests, and is the thing to run first if this
scraper ever comes back empty.

Two shapes of leaderboard:

* `shuffle-<class>-<spec>` and `blitz-<class>-<spec>` name the spec, so
  nothing has to be inferred.
* `2v2`, `3v3` and `rbg` mix every spec, so each entry's spec comes from
  the profile that is fetched anyway.

**The trap worth knowing about:** a player listed on
`shuffle-hunter-beastmastery` may be logged out as Marksmanship. Reading
their *active* spec files a Marksmanship loadout — Sentinel hero talent
and all — under Beast Mastery. The scraper matches the group whose spec
is the one the leaderboard is for, and takes the hero talent from that
loadout's `selected_hero_talent_tree` rather than from the character's
`active_hero_talent_tree`, for the same reason.

One build is kept per hero talent, from the highest-ranked player running
it: an "averaged" loadout code would be a code nobody plays. Talent sets
are genuinely comparable, so those are counted and the five most common
are kept.

**Coverage is not uniform, and the reason matters.** `shuffle` and
`blitz` reach all 40 specs because their leaderboards are per spec. The
mixed brackets cannot: a spec nobody queues in simply does not appear.
Sampling only the top of those boards makes it worse — the specs that
drop out first are the rare ones, which are exactly the ones whose data
is hardest to get anywhere else — so the whole board is read rather than
a slice of it.

Even then there is a ceiling, and it is worth knowing before someone
treats it as a bug: the EU rated battleground board carries about **172
entries in total**. Whatever fraction of the 40 specs appears in those
172 players is all the RBG data that exists. 2v2 and 3v3 are far larger
(roughly 5,000 and 3,600) and cover correspondingly more.

Credentials come from `~/.config/bnet/credentials` or the environment
(see `ccutil.bnet_credentials`). The file must not be readable beyond its
owner — the tools refuse it rather than warning. Nothing prints the
values, and `.gitignore` blocks `credentials` and `*.secret` in every
directory.

## Conventions in the generated Lua

* Keys that come from the data — spec slugs, context keys, difficulty
  labels — are always quoted (`["holy"]`), so they read as values rather
  than as field names. Structural field names are not.
* Dictionaries keep insertion order, so a rerun against unchanged sources
  produces an unchanged file and the diff shows only what really moved.
* Every file starts with a "generated, do not edit" line and its source.
